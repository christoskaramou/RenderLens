Khronos hosts the validation implementation; LunarG contributes to it and supplies SDK/configuration tools. Render Lens uses the published checking ideas, not those tools or layer output.

Source root: https://github.com/KhronosGroup/Vulkan-ValidationLayers/tree/99fd2cb5761410c0e8cd82395861abd75c9d1f06/layers/best_practices

| Implementation read | Upstream observation | Render Lens observation / limitation |
| --- | --- | --- |
| `bp_pipeline.cpp`, `PreCallValidateCreateGraphicsPipelines` | Multiple pipeline creations without a cache | Godot's pipeline-cache setting; no claim about individual Vulkan calls |
| `bp_wsi.cpp`, `PreCallValidateCreateSwapchainKHR` | Two swapchain images with a synchronized present mode | Configured image count plus VSync; actual driver choice is unknown |

All 16 adaptations are labeled heuristic, preserve vendor scope, carry an `upstream_check` identifier, and contain a concrete Godot condition and remeasurement step. Unknown vendors do not activate vendor-specific checks. Fifteen are in `gpu_best_practices.json`; the pipeline-cache adaptation is merged into `stutter.pipeline_cache_off` to avoid duplicate advice. Authored definitions are in `scripts/rules_api.py` and `scripts/build_rules.py`. The 1.9 and 1.10 additions and their narrower Vulkan-only scope are described below.

### Compute shader checks

Read `ValidateComputeShaderArm`, `ValidateComputeShaderAmd` in pinned [`bp_pipeline.cpp`](https://github.com/KhronosGroup/Vulkan-ValidationLayers/blob/99fd2cb5761410c0e8cd82395861abd75c9d1f06/layers/best_practices/bp_pipeline.cpp) and constants in [`bp_constants.h`](https://github.com/KhronosGroup/Vulkan-ValidationLayers/blob/99fd2cb5761410c0e8cd82395861abd75c9d1f06/layers/best_practices/bp_constants.h).

| New check | Exact predicate retained | Scope |
| --- | --- | --- |
| `compute_arm_large` | x*y*z > 64 | Arm only; upstream efficiency guideline, not a device limit |
| `compute_arm_alignment` | one invocation, or any dimension greater than one not divisible by four | Arm only; tested at aligned and unaligned boundaries |
| `compute_amd_alignment` | x*y*z not divisible by 64 | AMD only; cross-generation recommendation, not proof of a slow wave32 workload |

The plugin reads already imported `.glsl` [`RDShaderFile`](https://github.com/godotengine/godot/blob/4.4-stable/doc/classes/RDShaderFile.xml) resources and their [`RDShaderSPIRV`](https://github.com/godotengine/godot/blob/4.4-stable/doc/classes/RDShaderSPIRV.xml) bytes. It does not compile or dispatch shaders during an audit. The development test separately invokes Godot's compiler to verify real fixed and specialized outputs.

The bounded metadata reader follows [Khronos's SPIR-V grammar](https://github.com/KhronosGroup/SPIRV-Headers/blob/main/include/spirv/unified1/spirv.core.grammar.json): `OpEntryPoint`, `OpExecutionMode LocalSize`, `OpExecutionModeId LocalSizeId`, unsigned 32-bit constants, and the overriding `BuiltIn WorkgroupSize`. Specialization constants and expressions are not guessed. Malformed/truncated headers or instructions, unresolved dimensions, multiple entry points and oversized modules are skipped. This is not a replacement SPIR-V validator.

Coverage is returned by `scan_scene`, `audit_project_rendering` and `advise`: at most 64 imported GLSL files, eight versions per file, 1 MiB per module and 8 MiB each for imported resource files and compute bytecode per scan. Missing imports and skipped modules are reported. Runtime-generated shaders, high-level ShaderMaterial programs and unknown runtime specialization are outside coverage. File presence does not prove that a shader is dispatched. A separate configuration rule reports errors already recorded in an imported RDShaderFile or its shader stages.

Material observations use active overrides and overlays, including effective GPU-particle draw materials. Sharing a material with an ordinary mesh cannot hide its particle-specific shading finding, and repeated draw passes do not double-count that material. Next-pass chains are capped at eight materials per binding; `material_scan` exposes that cap and the number of truncated chains. Shared material checks retain a representative offending node per ordinary/particle use context. Per-surface tangent checks use `surface_get_format`, never mesh-buffer readbacks. Godot may populate tangent data when normals are supplied: tests explicitly accept that stored format rather than inferring missing tangents from the input arrays. Both triplanar modes generate tangent space in the material shader and are excluded from the missing-tangent warning. Unknown custom shader behavior is not guessed.

Lit feature candidates and anisotropy/tangent correctness are conservatively limited to Forward+ with the global vertex-shading override disabled. Per-vertex/unshaded material modes are excluded where the feature requires per-pixel lighting. Generic height-map advice is suppressed when the specific deep-parallax rule applies; triplanar height mapping is diagnosed as an ignored configuration instead of active parallax work.

The 120 estimated warmup-step and 256-voxel-dimension cutoffs are Render Lens review heuristics, not Godot device limits. SDF checks use the assigned texture rather than an unbaked resolution setting; a zero bake mask says nothing about an already assigned texture. Live world-scale checks honor compensating parent scale. Live viewport checks honor current-camera Environment overrides and world fallback; detached scans skip those observations. Configuration reflects the scanned moment and scripts may change it later.

All new counters have positive and negative fixtures. Tests also exercise renderer/version and forced-vertex-shading gates, overridden and shared materials, generated tangents, pass-chain truncation, camera overrides, world-scale compensation and parallax deduplication. These are detection tests, not evidence of a performance improvement on an arbitrary project or GPU.

### Native device compatibility checks

Pinned Khronos [`cc_spirv.cpp`](https://github.com/KhronosGroup/Vulkan-ValidationLayers/blob/99fd2cb5761410c0e8cd82395861abd75c9d1f06/layers/core_checks/cc_spirv.cpp) compares fixed workgroup dimensions and invocation products with physical-device limits. The plugin now makes the same two comparisons using Godot's current [`RenderingDevice`](https://github.com/godotengine/godot/blob/4.4-stable/doc/classes/RenderingDevice.xml):

| Rule | Source check | Godot observation |
| --- | --- | --- |
| `compute_invocation_limit` | `VUID-RuntimeSpirv-x-06432` | x*y*z exceeds `LIMIT_MAX_COMPUTE_WORKGROUP_INVOCATIONS` |
| `compute_dimension_limit` | `VUID-RuntimeSpirv-x-06429`, `y-06430`, `z-06431` | Any axis exceeds `LIMIT_MAX_COMPUTE_WORKGROUP_SIZE_X/Y/Z`; axes are combined into one finding |

These are compatibility findings about the imported shader and the current device, not captured validation messages or evidence that the shader ran. They are distinct from the 12 heuristic best-practice adaptations. `RenderingDevice::limit_get` reads immutable driver limits in both source tags and has no render-thread submission/guard. Actual GPU tests exercise the global device getter and real GLSL compiler. The audit never creates a device, compiles or dispatches a shader. Headless/OpenGL, zero/unavailable limits and unresolved specialization do not activate these checks. Reported `shader_scan.device_limits` makes the comparison's hardware scope explicit.

Height fields above their documented 1024 default and CanvasGroup margins above ten pixels are measurement candidates, not assertions of wasted time.
- CPU particle draw materials are GPU-rendered and now reach the existing material and per-pixel-shading checks. GPU trail shader flags remain invalid on CPU particles. Existing 2D/3D particle-animation checks now inspect CPU animation parameters as well, respecting effective overrides and unknown custom shaders.

Three further checks adapt GPUAV source ideas without instrumenting, compiling or dispatching shaders during an audit. ### Extended shader operands and native audio effects (1.14)

The same pinned [sanitizer pass](https://github.com/KhronosGroup/Vulkan-ValidationLayers/blob/99fd2cb5761410c0e8cd82395861abd75c9d1f06/layers/gpuav/spirv/sanitizer_pass.cpp) checks each component of GLSL Pow, Atan2 and FMin/FMax. Render Lens now recognizes negative Pow bases, zero bases with known nonpositive exponents, zero/zero Atan2 pairs, and literal NaNs in min/max. It accepts only the exact `GLSL.std.450` import, float32 scalars and direct 2–4 component vectors in the first compute entry block. Known components remain useful even when other components are dynamic. Scalar literal uint32-to-float32 bitcasts and constant-null vectors are included; arbitrary expression evaluation, helper functions, later blocks, specialization, vector concatenation and other widths remain excluded. Zero-divisor checks gain the same direct vector support. File presence does not prove execution.

Current [Khronos GLSL extended-instruction semantics](https://registry.khronos.org/SPIR-V/specs/unified1/GLSL.std.450.html) make the selected min/max operand implementation-dependent when NaN is involved, with special-value handling also affected by floating-point controls. The new min/max rule is therefore informational portability guidance, despite the pinned GPUAV diagnostic's stronger undefined-result wording. Fully literal expressions may be compiler-folded and leave no instruction to inspect. Out-of-range `textureGather` components are rejected by both Godot compilers and already covered by the existing shader compile-error rule; no duplicate rule is added. Compiler fixtures on 4.4 and 4.7.2 inspect real emitted bytecode without creating pipelines or dispatching invalid inputs.

Godot's native [pitch-shift processor](https://github.com/godotengine/godot/blob/4.4-stable/servers/audio/effects/audio_effect_pitch_shift.cpp) and [chorus processor](https://github.com/godotengine/godot/blob/4.4-stable/servers/audio/effects/audio_effect_chorus.cpp) were checked against their 4.7.2 counterparts. Non-unity pitch activates FFT processing; oversampling above the default four shortens the hop and increases processing demand. Oversampling greater than the configured FFT frame size makes the integer hop zero and is a separate correctness finding. FFT size is captured on instantiation, so the rule describes the resource configuration rather than claiming a running instance has already changed.

Chorus voices with zero cutoff are skipped natively; additional active voices each enter a sample loop. A wet mix of zero does not skip that loop, making a dry=1/wet=0 effect a bypass candidate only when upcoming automation does not need warm delay/filter history. The scan excludes disabled effect slots, bypassed buses and scripted/custom effects and reports uninspected enabled effects. It observes the current editor audio layout, which may differ from a layout replaced by game code; bus activity and audible contribution are unknown. Tests create disposable buses and cover defaults, boundaries, bypass/disable gates, script overrides and restoration without playing invalid DSP configurations. These are configured-cost candidates, not measured speedups.
